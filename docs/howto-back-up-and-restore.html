How to back up and restore files

You will create a backup, optionally encrypt it with a password, confirm the backup itself is intact, and restore files from it.

Prerequisites

  • STX-1 ULTIMATE System Monitor v3.0.0 or later installed
  • Somewhere to write the backup with enough free space
  • If you encrypt: a password you will not lose. There is no recovery path

Before you start, if you have older backups

Two things changed in v3.0.0 that affect backups made by earlier versions.

Encrypted backups made before v3.0.0 cannot be restored by those versions, because no decryption code existed at all. Every backup made with "Encrypt Backup" was unrestorable. v3.0.0 can still read the legacy format (src/SysMonitor.Core/Services/Backup/BackupEncryption.cs:26), so restore old ones with this version.

Backup verification used to check the wrong files. It hashed the live source files instead of the backup, so a corrupted backup verified clean and a healthy one failed once you edited the originals (src/SysMonitor.Core/Services/Backup/BackupService.cs). Re-verify anything you are relying on.

Steps

  1. Open Backup Manager from the navigation menu. In QUICK ACTIONS (15A), click NEW BACKUP.

  2. Choose a type:

Type Copies
FULL BACKUP Everything you selected
INCREMENTAL BACKUP Only what is new or changed since the previous backup with the same name, full or incremental (src/SysMonitor.Core/Services/Backup/BackupService.cs:125, :1608)

An incremental builds on the backup before it, and that one on the one before, back to a full backup: a chain. If nothing has changed, no backup is made. With no earlier backup of that name, or when the earlier one was encrypted with a different password (or not encrypted when this one is), the incremental starts a new chain and copies everything; the summary says which.

| SYSTEM IMAGE | Windows Backup's image of the system drive and every partition Windows needs to start (src/SysMonitor.Core/Services/Backup/SystemImage.cs) |

A system image has no sources or options to choose: after the type, pick the drive to save it on, which cannot be the drive Windows is on. It must be an NTFS drive (a USB drive formatted FAT32 or exFAT is refused, with the reason) or a network folder such as \\nas\backups. The app shows where it goes and about how much space it needs, then Windows asks for administrator permission and Windows Backup (wbadmin) writes the image to WindowsImageBackup at the root of that drive. The progress shown is Windows Backup's own, and its report is kept in %LocalAppData%\SysMonitor\Logs. Later images on the same drive add only what changed; a network folder keeps only the newest. Cancelling asks Windows Backup to stop, and Windows asks for permission again.

  1. Select the folders to back up, then the destination.

  2. Set the options.

If you tick Encrypt Backup, the format is PBKDF2-HMAC-SHA256 with 600,000 iterations, AES-256-CBC, and encrypt-then-MAC with an HMAC-SHA256 tag that is verified before any plaintext is written (BackupEncryption.cs:20-22, :31, :261). In practice that means a tampered backup fails to restore rather than quietly handing you altered files.

Compression can be None, Normal or Maximum. With None the backup is a folder rather than a single file, which is fine and is no longer a failure case (BackupService.cs).

  1. Click START BACKUP and wait for the summary. CANCEL BACKUP stops it.

Verification

In HISTORY (15B), use the Verify backup cap on the completed backup. It hashes the backup and checks it against what was recorded at the time it was written.

This is worth doing now rather than on the day you need it, because until v3.0.0 it was checking the wrong thing.

Restoring

In HISTORY (15B), use the Restore backup cap on the backup you want. The app asks first, saying what will be restored and where. The Delete backup cap beside it is red and asks before it removes anything.

Restore decides where files go, rather than trusting the path recorded inside the archive. Destinations are planned up front and confined to the folders the backup was taken from, and anything refused is reported to you rather than silently skipped (BackupService.cs).

That matters because before v3.0.0 an edited backup file could write its contents anywhere you could write, including your Startup folder.

A system image is not restored from inside Windows. Open Settings > System > Recovery, choose Advanced startup > Restart now, then Troubleshoot > Advanced options > System Image Recovery. It replaces everything on the drives in the image. Its Restore backup cap in HISTORY says the same, Verify backup says Windows Backup checked it as it was written, and Delete backup only takes it off the list: Windows manages its files (Control Panel > Backup and Restore (Windows 7) > Manage space).

Restoring an incremental puts back every file as it was when that incremental was taken, reading each one from the newest backup in its chain that holds it. A file deleted before the incremental was taken is not restored. An encrypted chain asks for its one password.

A backup that a later incremental builds on cannot be deleted while that incremental exists: delete the newer incrementals first. "Keep last" never removes one either, so a long chain keeps its full backup; make a new FULL BACKUP now and then to start a fresh one.

Troubleshooting

The password does not work. There is no recovery. The key is derived from your password with 600,000 PBKDF2 iterations, which is the point.

Restore reported refused entries. Those files pointed outside the folders the backup covered, so they were not written. The report names them. This is the safety check doing its job.

An incremental will not restore: a backup it builds on is missing. One of the backups in its chain was deleted or moved outside the app. Nothing is written; restore the newest full backup instead, or move the missing backup back.

A system image is refused for a drive. The message says why: it is the drive Windows is on, it is not NTFS, it is a mapped network drive (choose its \\server\share folder instead), or it is not connected. If Windows Backup itself fails, the message quotes its error and names the report in the Logs folder.

Verification fails on a backup that used to pass. If the backup was made before v3.0.0, the original pass may have been meaningless, because verification hashed the source files. Make a fresh backup.
